# ツール権限の申請 (Discord 承認)

> 足りない許可を、人間がボタンを押したときだけ増やす仕組み。
> 入口は [README](../../README.md)、導入手順は [SETUP.md](../../SETUP.md)。

許可されていないツールを claude が使おうとすると、結果 JSON の `permission_denials` に残る。
ブリッジはそれを **承認カード** に変えてスレッドへ出す。**エージェントは申請しかできず**、
許可が増えるのは `allowedUserIds` の人間がボタンを押したときだけ。

カードには**経路が 2 つ**あり、押したときの意味が違う。文面と見出しで書き分けてある:

| | 出るタイミング | タップ数 | 効き始め |
| --- | --- | --- | --- |
| job 終了後 (全チャンネル) | 結果 JSON の `permission_denials` から | 2 段階 | **次の job から** |
| 実行中 (`hooks: true` のみ) | ツールを呼ぶ直前に PreToolUse hook が問い合わせる | 1 タップ | **止まっているその job がそのまま続く** |

- job 終了後の経路は「承認する」→「恒久設定として確定」の **2 段階**。誤タップ 1 回で恒久設定が
  入らないようにしてある (確定できるのは承認を始めた本人だけ)
- 実行中の経路は「承認して続行」の **1 タップ**で保存まで進む。job が止まって待っている状況で
  2 タップを挟むと、その間ずっと作業ディレクトリのレーンが塞がるため
- **どちらも保存が通ってから承認済みにする**。clone → 一時ファイル → rename 成功 → メモリ差し替え →
  台帳確定の順で、途中で失敗したら「保存に失敗したためまだ何も許可していません」と返して
  押し直せる形に戻す (メモリにだけ許可があってディスクには無い、という食い違いを作らない)。
  実行中の経路で hook に `allow` を返すのも保存の後ろ — でないとディスクに無い許可でツールが走る
- 承認ぶんは `data/tools-extra.json` に積み、**`config.policy.json` は書き換えない** —
  手書きの正本と承認由来を混ぜないため
- 申請は nonce で guild・channel・thread・bot・チャンネル設定・作業ディレクトリへ束縛する。
  **期限は既定 30 分** (`limits.toolApprovalTtlMs`・1 分〜24 時間)。
  期限切れ・却下・ブリッジ再起動では**何も許可しない**
- 1 job に出すカードは既定 3 件まで (`limits.maxToolApprovalCards`・1〜10)。超えた分は件数を明示して出さない。
  どちらも範囲外の値は起動時に落とす (実質無期限・無制限になる設定を通さない)

### 実行中に待つ経路 (`hooks: true`)

`hooks: true` のチャンネルでは、承認カードにできるツールを呼ぶ**直前**に PreToolUse hook が
ブリッジへ問い合わせ、**人間がボタンを押すまで job を止める** (実測: hook は 60 秒以上
ブロックでき、`allow` は実際に権限を付与する)。押されたら同じ job がそのまま続行する。

- **待ち上限は既定 3 分** (`limits.toolApprovalWaitMs`・30 秒〜10 分)。押されないまま過ぎたら
  拒否として job を続け、カードは「⌛ この申請は無効になりました」に理由付きで畳む
  (押した人が居ないので「却下しました」とは書かない)。上限を短くとってあるのは、
  **待っている間ずっと同じ `cwd` のレーンを占有する**ため — 他チャンネルの job も止まる。
  待機中は ⏳ の代わりに `🔐 承認待ち…` が出るので、何で止まっているかは分かる。
  **待ち上限はカードの期限 (`toolApprovalTtlMs`) より短いことを起動時に検証する** —
  逆だと「押せなくなった後も job が止まり続ける」設定になる (実効値同士で見るので、
  片方だけ書いて省略側の既定と噛み合わない組み合わせも落ちる)
- **押されない・期限切れ・カードを投稿できない・カードのメッセージ ID を束縛できない・
  job の中断・ブリッジ停止は、すべて拒否**。判定が付かない側に倒す。
  待機を残したまま申請を消す口があると hook が永久に待ち、その job は二度と進まない
- 聞く対象は**承認カードにできるツールだけ** (いまはドメイン限定の `WebFetch`)。
  `--allowedTools` は許可リストではなく追加許可で、指定外でも無害なものは通るため、
  全ツールに載せると通るはずの呼び出しにまでカードが出る。
  **grant にできない要求 (シェル・パス・https 以外) はここで裁かず claude の通常判定へ戻す** —
  hook が無かったときより厳しくしない
- **既に許可・承認済みのものは聞かずに通す。** 承認済みルールは job 開始時点のスナップショットで
  渡しているが、この経路だけは「実行中に承認したぶんもその job で効く」— 意図的な例外
- hook とブリッジは別プロセスなので、やり取りは job 専用ディレクトリのファイル 2 枚
  (`<id>.ask.json` / `<id>.ans.json`) で行う。localhost にポートは開かない。
  tmp へ書いて rename し、**読めない・壊れているは拒否**
- 待ち上限は **ブリッジ (3 分) < hook 自身の打ち切り (+5 秒) < CLI の hook timeout** の順。
  CLI に kill されるとカードが「承認待ち」の見た目のまま残るので、正規経路は必ずブリッジ側の拒否になる
- 実行中に聞いたルールは、job 終了後にカードを出し直さない (人間はもう答えている)。
  同じルールの重複と 1 job のカード上限は、**投稿の往復より前に枠を取って**守る —
  ask は並行して届くので、投稿してから記録すると全部が「まだ聞いていない」判定になる

**自動承認できるのは 1 種類だけ。** 入力を確実に束縛できるものに限る:

| 種類 | 対象ツール | 申請される形 | 範囲 |
| --- | --- | --- | --- |
| `web-domain` | `WebFetch` | `WebFetch(domain:example.com)` | このドメインだけ (https のみ) |

**シェルコマンドは自動承認しない。** claude は照合前に `timeout` や裸の `xargs` のような
wrapper を外すので、「コマンド文字列の完全一致」では実行されるコマンドを固定できない
(承認済みコマンドを `xargs` 経由にすれば実行時に引数を足せる)。生文字列一致を保証するには
PreToolUse hook が要る — **その配管は上記のとおり通ったが、種類を増やすのは別の作業**。
hook の payload は生の `tool_input` を持つので技術的には可能で、混ぜると変更範囲が
破綻するため段階を分けてある。

**ファイルパスも自動承認しない。** claude のパス指定子は完全一致ではなく gitignore パターンで、
job 実行中に対象がディレクトリへ差し替わると「1 ファイルだけ」を保証できない。

どちらも、安全に書ける場合にかぎり**人間が `config.policy.json` へ貼れる候補**を警告つきで文字列表示する
(カードにも保存にもしない。貼るかどうかと範囲の見極めは人間の仕事)。パス候補は `./` でアンカーし、
`Write` / `NotebookEdit` は claude が実際に照合する `Edit(パス)` として出す
(`Write(パス)` は受理されても照合されない — 実測 CLI 2.1.220)。
MCP・`WebSearch`・`Task`・`Glob`/`Grep` は入力を束縛できないので候補も出さない。

**保存するのはルール文字列ではなく構造化 grant** (`{kind, tool, value, cwd, …}`)。ルール文字列は
読むたびに組み立てる — 記法が変わっても移行でき、保存値と表示値が混ざらない。生成・登録・保存・
読込・job 開始の**すべてが同じ検証関数を通る**ので、未知の `kind`・余分なキー・wildcard・裸のツール名・
不正な cwd は保存時にも読込時にも捨てられる。スキーマ版が違うファイルは読まない (fail-closed)。

**作業ディレクトリは job を受け付けた時点で 1 回だけ実体へ固定する。** レーンの鍵・CLI の
`cwd`・セッション記録・承認の照合・拒否の申請は、すべてこの同じ値を使う。生のパスを持ち回ると、
junction を job の途中で差し替えたときに「A で起きた拒否が B 向けの承認として保存される」
「resume が別の実体へ続く」といった食い違いが起きる。解決できないパスの job は受け付けない。
grant の `cwd` は**正規形そのもの**でなければ検証を通らない (`C:\…` と `C:/…` の表記違いで
「承認も保存も成功したのに次の job で一致しない」を起こさないため)。
`config.policy.json` の `cwd` を別リポジトリへ向け替えると過去の承認は効かなくなる。

**「保存できなかった」と「既に保存済み」は区別される。** 保存層は
`{ok: true, added}` / `{ok: false, reason}` を返し、`ok` でなければ承認は確定しない
(カードは確認段階へ戻り、もう一度確定を押せる)。両方を同じ偽値で返していた頃は、
保存ゼロなのに「恒久設定として保存しました」と表示できてしまった。

**候補にもしないもの** (理由だけ返す。必要なら人間が `config.policy.json` に直接書く)

| 対象 | 理由 |
| --- | --- |
| コマンド・パスの指定なし | ツール全体の許可に化ける |
| wildcard (`git *`) / glob・特殊文字 (`file[1].js`) | 範囲が広がる・誤一致する |
| シェルの連結・置換・クォート (`;` `&&` `\|` `` ` `` `$()` `>` 等) | 別のコマンドを走らせられる |
| cwd の外を指すパス (`..`・絶対パス・リンク先が外) | 作業ディレクトリの外へ出る |
| ディレクトリ | gitignore 意味論で配下すべてが対象になる |
| http / IP / localhost の取得先 | 内部宛や平文の取得を恒久許可にしない |
| 秘密らしい語・長いトークン列 (`.env`・`id_rsa`・`*_key`・`api-key-….example.com` 等) | 承認ログと Discord に秘密を残さない |
| 値の前後に空白があるもの | trim すると「別の値」を承認したことになる |
| 表示のために形が変わるもの (バッククォート・制御文字を含む) | 貼っても効かない候補を見せない |

**保存値は無加工。** バッククォートや制御文字を潰すのは Discord へ描くときだけで、
保存された grant には触らない (潰した文字列を保存すると別の値を承認したことになる)。
監査ログに出すのも grant の指紋 (`web-domain/WebFetch#<sha256 前 16 桁>`) と文脈だけで、値そのものは残さない。
