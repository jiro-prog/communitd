# 委譲契約 (構造化)

> 委譲の 5 部を構造として受け取り、touch 集合を実際の権限へ変換する仕組み。
> 入口は [README](../../README.md)、導入手順は [SETUP.md](../../SETUP.md)。

役割文の先頭に `<!-- communitd-schema: delegation -->` / `<!-- communitd-schema: report -->` を
書いた bot は、最終出力が `--json-schema` でスキーマに拘束される。**宣言の無い bot・
ランタイム (codex) は完全に従来どおり**動く。

- **Discord に出るのは `body` (本文) フィールドだけ。** `--json-schema` を渡すと `result` は
  スキーマの JSON 文字列そのものになる (実測 CLI 2.1.220) ので、散文の置き場をスキーマの中に
  持たせてある。制御フッターも `body` の末尾に置かれ、**抽出と無害化は従来と同じ経路**を通る
- 委譲は `{body, background, purpose, touch_set[], acceptance[], stop_conditions[], touch_restricted?}`、
  報告は `{body, changed_files[], did[], verification, remaining[]}`。様式の正本は
  `src/contract.js` の 1 か所で、役割文には「検査される」ことだけを書く (二重管理にしない)
- **スキーマのキーは ASCII でなければならない。** 日本語のプロパティ名を渡すと API が
  `400 … Property keys should match pattern` を返し、構造化出力そのものが返らない
  (実測)。人間向けの呼び名は `FIELD_LABELS` と各フィールドの説明文が持つ
- **様式に合わなければ素の `result` を投稿して情報は落とさない**が、契約としては使わない
  (保存も touch 制限の適用もしない = 権限は増えない)。スレッドには警告が出る
- 長すぎるフィールドは**黙って切らずに不適合**にする。切ると本文末尾の制御フッターごと
  消えて handoff が落ちるため。スキーマ側にも同じ上限 (`maxLength` / `maxItems`) を書いて
  あるので、モデルは生成時点で守れる (API が受理することは実測済み)
- 契約は `data/contracts.json` に **thread・委譲元・宛先・作業ディレクトリへ束縛して**保存し、
  **呼ばれた相手の次の 1 job** にだけ効く。人間が直接呼んだ job には適用しない
  (取り出したら消すので、同じ契約が二度効くこともない)
- **委譲だけでなく報告も持ち回る。** 報告は次の検収 job へ「変更ファイル / やったこと /
  検証結果 / 残課題」として注入され、検収がフィールド照合になる (変更ファイルは自己申告なので、
  スレッドの `📋 git status 差分` と突き合わせろとブロック側に書いてある)
- 保存は**宛先ごとの FIFO キュー**。単一値で持つと、同じ相手へ続けて委譲したとき後の契約が
  前を上書きし、**1 本目の job に 2 本目の契約が効く** (job はキューで待つので、保存と消費は
  1 対 1 に並ばない)。配送に失敗したときは**その 1 件だけ**を id で取り消す
  (宛先ごと消すと同じ相手宛の他の契約が巻き添えになる)
- 取り出すのは **thread・宛先・送信元がすべて一致した 1 件だけ**。合わないものは残す。
  **人間が直接呼んだ job はストアに触れない** — 触って捨てると、あとから走る本来の
  handoff job が契約なしで起動し、touch 制限が黙って外れる
- 取り出し (claim) は **job の受付時**に済ませて job に束縛する。開始時まで残すと、
  待機中に `/stop`・`/restart force` で取り消された job の契約がストアに居座り、
  次の handoff がそれを消費して対応がずれる (取り消された job の契約は一緒に捨てられるのが正しい)
- 契約と制御メッセージには**投稿より前に決めた同じ nonce** を載せ、完全一致で結び付ける
  (制御メッセージの末尾に `` `契約:xxxxxxxx` `` が付く)。投稿後にメッセージ ID を書き戻す形だと、
  受け手の `MessageCreate` が書き戻しより先に届いたときに取りこぼし、契約なし = touch 制限なしで
  起動してしまう。この nonce は**起動には一切関与しない** — 呼び出しは従来どおりメンション 1 個だけ
- **タグが付いた handoff なのに契約が見つからなければ job を起動しない。** 「契約なしの handoff」と
  「契約を失った handoff」を区別できるのがタグの主目的で、後者を素通しすると制限が黙って外れる
- 消費されないまま **24 時間**過ぎた契約は掃除する。**保存の上限判定より前**にも掃除するので、
  起動しなかった handoff の契約が溜まって「新しい委譲を保存できない → claim も起きない →
  掃除されない」と閉塞することはない (保存時刻を読めない契約も同じ扱い)
- 未消費が上限 (5 件) に達したら、**古い方を捨てず新しい保存を失敗させて handoff を止める**。
  捨てられる契約に対応する handoff は既に配送済みなので、捨てると対応がずれ続ける
- **保存できなければ handoff を止める** (契約なしで相手が走ると絞ったつもりが絞られていない)。
  配送に失敗したときは保存した契約を取り消す — 呼べていない相手の契約を残さない
- `受入基準` は**コマンドとして実行しない**。モデルが書いた文字列を実行すると、作者管理の
  `verify` とは別の実行経路になる (`--settings` の `permissions` を禁止キーにしたのと同じ判断)

### touch 集合 → 実権限

`touch制限` が有効な job (省略時は有効) では、touch 集合が**実際の書込み権限**になる。
規律ではなく機構で、集合の外を編集しようとするとツール側で拒否される。
**この拒否は承認カードにはならない** — 実行中のカードはドメイン限定の `WebFetch` だけが対象で、
ファイルの書込みは自動承認できる種類に入っていない。集合の外が要るなら**委譲をやり直す**。

**次の 5 点セットで初めて強制になる** (どれか 1 つでも欠けると素通りする —
実測 CLI 2.1.220):

| 手段 | 無いとどうなるか |
| --- | --- |
| `--permission-mode default` へ狭める | `acceptEdits` は `Edit(パス)` の照合を**丸ごと迂回**する (touch 外が書き換わった) |
| `--setting-sources ''` で外部 settings を落とす | user / project の `permissions.allow` が `--allowedTools` に**勝って権限を付与する**。`permissions.allow: ["Edit"]` を 1 行足すだけで破れた |
| `--tools` を読み取り系 + `Edit` に限定 | 組み込みツールが残り、別経路で書ける。**空集合も明示的に渡す** (省略すると全ツールが使える) |
| `--allowedTools` の書込みを `Edit(./パス)` だけにする | 裸の `Edit` が残ると全ファイルが対象になる |
| `--disallowedTools` で明示的に落とす | `Agent` / `Task` は**指定しなくても呼べる**ため、省略では止まらない |

加えて `--strict-mcp-config` で MCP を遮断し、**参照ディレクトリ (`claudeAddDirs`) も開かない**
(`--add-dir` は読取専用にできないので、残すと touch 集合どころか作業ツリーの外へ書ける)。
落とすのは `Bash` / `PowerShell` / `Write` / `NotebookEdit` / `Agent` / `Task`。

- `--setting-sources ''` は**外部 settings だけ**を落とす。job 専用の `--settings` (hooks) は
  別枠なので、承認カード・verify・ツール軌跡はそのまま動く (実測で hook の発火を確認)。
  管理者ポリシー (managed settings) は仕様上どのみち残る — これは機械の持ち主の制御であって
  ブリッジより上位
- ただし外部 settings は `permissions.allow` (広げる) だけでなく `permissions.deny` /
  `permissions.ask` / `PreToolUse` hook (狭める) も持ちうる。CLI に「許可だけ落とす」指定が
  無いので、**読める外部 settings にそれらが書かれていたら touch 制限の job を起動しない**。
  その制限を `config.policy.json` 側へ移すか、touch 制限を解除して委譲し直す
- **touch 制限つきの委譲は claude ランタイムの担当にしか渡せない。** codex ランタイムの権限は
  `codexSandbox` の 2 値でパス単位に絞れないので、渡す前 (契約の保存前) に止めて handoff しない。
  制限を解除した委譲なら渡せる (その契約は権限ではなく依頼文の構造化にすぎない)

- **絞る方向にしか使わない。** 変換の入力はチャンネルの実効権限で、出力はその部分集合。
  元が読み取り専用なら touch 集合を書いても書込みは付かない (契約が権限を増やす経路を作らない)
- 元が**既にパス限定**のチャンネル (`Edit(./src/a.js)` だけ持つ) では、touch 集合に別のパスを
  書いても**広がらない**。claude のパス指定子は gitignore パターンで、あるパスが既存ルールに
  含まれるかを文字列から安全には言えないため、**完全一致だけ**を通す。書込み権限はあるのに
  touch 集合と 1 件も重ならないときは、何も書けない job を走らせず理由を見せて止める
- `Write(パス)` は受理されても照合されない (再実測済み) ので、書込みは `Edit(パス)` に一本化する
- cwd の外・ディレクトリ・ワイルドカード・特殊文字・秘密らしい語を含むパスは**絞り込みに使わない**
  (判定は承認候補と同じ `src/toolrules.js` の 1 か所)。落ちた分は契約ブロックとログに出す
- **Windows が特別扱いするパスも拒否する**: `:` (NTFS の代替データストリーム —
  `src/index.js:shadow` は index.js に隠れて書ける)、`CON` / `NUL` / `COM1` / `CONIN$` /
  `COM¹` などの予約デバイス名 (拡張子を付けても予約のまま)、末尾の空白・ドット。どれも
  **通常のファイルにならず git 差分にも出ない**ので、書かれても検収から消える
- **リンクを経由するパスも拒否する。** cwd の外を指すものだけでなく、`alias/x.js` →
  `real/x.js` のように **cwd の中で完結するリンク**も落とす。ルールが指すのは字句上のパスなので、
  実体がずれていると touch 集合に無いファイルへ編集が届く
- **hardlink のあるファイル (`nlink > 1`) も拒否する。** realpath では見抜けない —
  別名ではなく同じ実体そのものなので、集合の中の名前を編集しただけで集合の外の名前からも
  同じ変更が見える
- **効くのは既存ファイルの編集だけ。** `Edit` は既存ファイル専用で、新規作成に要る `Write` は
  落としてあるので、touch 集合に**まだ無いファイルを書いても編集できない** (拒否として出す)。
  ファイルを増やす依頼は touch 制限を解除する
- **`permissionMode` は絞る向きにしか動かさない。** `acceptEdits` / `bypassPermissions` は
  `default` へ落とすが、**`plan` (読取専用) は据え置き** — 上げると読めるだけだった job が
  書けるようになる。表に無いモードは安全性を証明できないので job を起動しない
  (`config.policy.json` の `permissionMode` は起動時に列挙で検証する)
- **1 件も変換できなければ job を起動しない。** 「絞れなかったので元の権限で走らせる」は
  契約を無視して走るのと同じ (fail-open にしない)
- shell が要る作業・探索的な依頼は `touch制限: false` で委譲する。テスト実行はチャンネルの
  `verify` に委ねる (ブリッジが別プロセスで実行するので job の権限とは無関係)

**保証範囲 (ここが境界)。** touch 制限が縛るのは**エージェントが直接ツールで書き込む範囲**だけで、
**編集されたコードの実行時の副作用は縛らない**。`verify` はリポジトリのコードを OS 権限のシェルで
実行するので、touch 集合の中に書いたコードは集合の外へも書ける。これは PR の CI と同じ性質の境界で、
実行自体を止めない限り塞げない (止めると verify ゲートが失われ、shell を落としたワーカーは
テスト信号を持てなくなる)。**防御は従来どおり検収が持つ**:
レビューと、スレッドの `📋 実行前後の git status 差分` の突き合わせ。

**管理者ポリシー (managed settings) があるチャンネルでは touch 制限 job を起動しない。**
`--setting-sources` の対象外で優先度も上、同じ permission 形式なので、裸の `Edit` 許可が
書かれていても打ち消せず、読めなければ中身も分からない。**存在を検出したら止める**
(`C:\ProgramData\ClaudeCode\managed-settings.json` 等)。
