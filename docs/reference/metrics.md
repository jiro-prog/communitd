# 計測ログ

> job ごとの所要時間とトークン使用量をどこにどう残すか。
> 入口は [README](../../README.md)、導入手順は [SETUP.md](../../SETUP.md)。

job が 1 本終わるたびに `console.log` へ 1 行出る:

```
[job 3f2a1b7c worker thread:1399…] queueWait 1.2s / run 62.1s / prompt 18420 chars (role 4180) / ctx 12 件 (省略 0) / tok in 3.2k, out 2.0k (cacheR 470k, cacheW 6.1k) / tools 21 件 (編集前 Read 5) / verify 4.3s (pass, 1 runs) / ok
```

待ち時間 (レーンが空くまで) と実行時間を分けているのは、「遅い」の原因が
**キュー待ちなのかモデルの実行そのものなのか**をログだけで切り分けるため。
`prompt` は実際にランタイムへ渡した総文字数で、うち role (共通規定 + 役割文 + 実行文脈) の分を
括弧に併記する — 本文だけ数えると role を厚くした分が計測から消えるため。`ctx` は文脈に載せた
発言数と、文字数予算で落とした件数。

`tok` は**実消費**の側 (claude ランタイムのみ — `usage` を返さない codex では出ない)。
`prompt` の文字数はブリッジが渡した分しか数えないので、**セッションが抱えている履歴**
(`--resume` が毎リクエスト読み直す分) が見えない。実測ではトークン消費のほぼ全部が
キャッシュ読みなので (2817 リクエストで入力の 95%)、in / out に畳まず
`cacheR` (再利用) と `cacheW` (再作成) を分けて出す。読み方は 2 つ:

- `cacheR` が回を追って伸び続ける = セッションに履歴が堆積している。**消費はターン数の
  2 乗で効く**ので、長寿命スレッドではここが支配的になる
- `cacheW` が跳ねた job = キャッシュの前方一致が切れた job。実機の TTL は 1h で
  (実測: `usage.cache_creation.ephemeral_1h_input_tokens` に載る)、
  1h TTL の書込みは基準入力の 2.0 倍・キャッシュ読みは 0.1 倍 — **同じトークン数でも
  書込みは読みの約 20 倍の重み**になる。数十 k を超えて跳ねているなら原因を追う価値がある。
  ただしこの倍率は**料金表どうしの比**で、認証はサブスクの継承なので (`src/claude.js`)、
  usage 上限が実際にこの比で数えられている保証はない。桁感として使う

`tools` はその job が実行したツールの総数で、括弧に
失敗した件数 (0 なら書かない) と**最初の編集までに読んだ回数**を併記する — 毎回大量に
読み直しているなら、ハーネスが渡すべき文脈をモデルが探し直している。
`verify` は検証の合計時間・成否・試行回数で、未設定・spawn 前失敗・停止では出ない。
末尾は終了理由 — `ok` / `verify-failed` / `aborted` (`/stop`) / `failed(...)` / `deliver-failed` /
`protocol-mismatch` / `role-unreadable` / `stopped-before-start` / `internal-error`。
job ID は並走した job のログが混ざっても 1 本を追うためのもの。
**JSONL のような機械可読の計測基盤は作らない** — この規模ではこの行を grep すれば足りる。
